Eternal Quest: World

언리얼 데디케이티드 서버와 AWS 인프라를 연동해 인증부터 게임 접속까지 직접 구축하고 운영한 온라인 RPG입니다.

게임 소개
언리얼 데디케이티드 서버와 AWS 인프라를 활용한 온라인 RPG
진행 기간
2026.08.24 ~ 2026.09.27

프로그래머 1명
사용 기술

담당 파트
인증 서버·채널 시스템 구현 및 클라우드 인프라 고도화
언리얼 데디케이티드 서버 빌드 및 AWS 배포

아키텍처

주요 구현

C++ 기반 인증 서버·채널 시스템 구현

  • 게임 계정 인증 REST API 서버를 C++로 구축, 회원가입·로그인·토큰 검증 제공
  • PBKDF2 비밀번호 해싱, JWT 인증, SQL 인젝션 방어, 로그인 실패 시 계정 잠금 적용
  • 채널 조회·라우팅 API를 별도 서비스로 분리, 인증 서버의 JWT로 세션 없이 인증 처리
  • 멀티스테이지 Dockerfile로 빌드·런타임 환경 분리, non-root 유저로 컨테이너 실행

AWS 인프라 고도화

  • ALB + ASG로 인증 서버·채널 시스템 오토스케일링, 부하 테스트로 임계값 초과 후 스케일 아웃 확인
  • 자체 관리 DB를 RDS로, 채널 저장소를 ElastiCache로 전환, Multi-AZ 페일오버 66초·23초 실측
  • CloudWatch 알람 기반 EC2 Auto Recovery와 systemd로 장애 자동 복구, S3 로그 아카이빙 자동화
  • 데디케이티드 서버 2대로 인증 → 채널 선택 → 접속 흐름 검증, 온디맨드 운영으로 상시 운영 대비 약 95% 비용 절감

언리얼 데디케이티드 서버 배포

  • 언리얼 엔진을 Windows에서 Linux 타겟으로 크로스 컴파일해 데디케이티드 서버 빌드
  • AWS EC2(Ubuntu) 인스턴스에 보안 그룹, SSH 접속 환경 구성 후 서버 배포
  • 채널별 서버 2대에 탄력적 IP와 포트(7777·7778)를 고정해, 인스턴스를 재시작해도 접속 주소 유지

크로스 컴파일 빌드 파이프라인 트러블슈팅

  • Linux 심볼 생성에 필요한 바이너리(dump_syms, BreakpadSymbolEncoder) 부재로 인한 연쇄 빌드 실패 진단
  • UnrealBuildTool(LinuxToolChain.cs)을 직접 수정해 Linux 바이너리를 WSL로 실행하도록 바꾸고 심볼 생성 단계 우회
  • 크래시 심볼 추적이 불가능해지는 트레이드오프를 문서화해 개선 과제로 관리

설계와 문제 해결

상태 유무에 따른 확장 방식 분리

  • 인증 서버·채널 시스템은 요청마다 독립적으로 처리되는 무상태 구조라, ALB 경로 기반 라우팅 뒤에 ASG로 수평 확장
  • 데디케이티드 서버는 플레이어 위치·전투 상태를 메모리에 유지해, 인스턴스를 교체하면 진행 중인 게임 상태가 유실됨
  • 확장 대신 같은 인스턴스를 복구하는 방식을 택해, 프로세스 장애는 systemd, 하드웨어 장애는 EC2 Auto Recovery로 대응
  • 프로세스 강제 종료 시 5초 이내, EC2 재부팅 후 systemd로 1~2분 내 서비스 자동 기동 확인

CPU 대신 요청 수 기준 스케일링

  • 인증 서버는 PBKDF2 해싱으로 CPU 부하가 크지만, 채널 시스템은 Redis 조회 대기가 많아 부하가 높아도 CPU 사용률이 낮게 나타날 수 있음
  • CPU 기준으로는 채널 시스템 과부하 시 스케일 아웃이 되지 않을 수 있어, 두 서비스에 공통으로 쓸 수 있는 RequestCountPerTarget으로 정책 설정
  • 로그인 요청 150건을 동시에 보낸 부하 테스트 도중 스케일 아웃 트리거 확인

DB 복구 가설 검증

  • RDS 전환으로 장애 복구 시간이 단축된다는 가설을 세웠으나, 1차 측정에서는 RDS 재부팅 43초, 기존 MariaDB 컨테이너 재시작 7초로 예상과 반대 결과
  • 프로세스만 다시 띄우는 컨테이너 재시작과 OS 전체를 재부팅하는 RDS는 비교 범위가 다르고, 둘 다 하드웨어 장애 상황이 아니어서 판정 보류
  • RDS를 Multi-AZ로 전환해 강제 페일오버를 트리거, 66초 만에 사람 개입 없이 자동 복구 실측 (자체 관리 방식은 백업 복원에 수 시간 소요 추정)
  • 검증 후에는 비용을 고려해 Multi-AZ를 해제하고 단일 인스턴스로 운영

관리형 캐시 이중화 전환

  • 채널 상태는 이관이 필요 없는 TTL 90초 임시 데이터라, Primary·Replica를 서로 다른 AZ에 둔 ElastiCache 복제 그룹을 새로 만들어 교체
  • 채널 시스템 컨테이너 설정의 캐시 엔드포인트를 새 Primary로 바꿔 재생성하고, 연결을 확인한 뒤 기존 단일 노드 클러스터 삭제
  • 강제 페일오버 시 23초 이내에 Primary가 다른 AZ의 노드로 전환되는 것 확인

TTL 기반 채널 상태 판정

  • 데디케이티드 서버가 30초마다 접속자 수를 채널 시스템 내부 API로 보고하고, 채널 시스템은 이를 Redis에 TTL 90초로 저장
  • 조회 시 키가 없으면 unknown, 최대 인원 이상이면 full, 그 외는 open으로 판정해 별도 헬스체크 없이 서버 다운을 감지
  • TTL을 보고 주기의 3배로 두어, 보고가 한두 번 누락되는 일시적 지연에는 바로 unknown으로 판정되지 않도록 함
  • 내부 보고 API는 ALB 별도 경로와 내부 토큰으로 분리해 외부 클라이언트의 임의 호출 차단

운영 트러블슈팅

  • 재빌드 시 실행 설정 초기화: 패키징 과정에서 실행 스크립트가 기본 템플릿으로 재생성돼 포트·맵 설정이 사라지는 문제를, 빌드 도구가 건드리지 않는 별도 실행 스크립트로 설정을 분리해 해결
  • DB 마이그레이션 시 계정 미이관: mysqldump가 사용자 계정과 권한을 옮기지 않아 인증 서버의 DB 접속이 실패, CREATE USER와 권한 부여를 별도로 수행하고 레코드 수·해시값으로 정합성 재확인

운영 자동화와 비용 관리

  • 사용할 때만 인프라를 켜도록 EC2·RDS 정지와 재시작, ASG 희망 용량 조정을 Bash 스크립트로 일괄 처리
  • RDS는 정지 후 7일이 지나면 자동으로 다시 시작되는 점을 확인해 비용 관리 절차에 반영
  • 데디케이티드 서버 로그를 cron으로 매일 자정 S3에 채널별로 백업해, 인스턴스가 교체돼도 사후 분석 가능
